# 技術要件

このMVPの主目的は、実際の小規模Webアプリを通じてTopcoatのサーバー描画、部分更新、および開発体験を検証することである。網羅的な自動化基盤の構築は目的に含めない。

## アプリケーション構成

- RustとTopcoat 0.4.0を使用し、依存バージョンを完全固定する。
- `rust-toolchain.toml`でRust 1.95.0を固定し、`rustfmt`と`clippy`コンポーネントを同じツールチェーンで使用する。
- Topcoatのサーバー描画と部分更新を使用する。
- UIの基本部品には、`topcoat ui` CLIでプロジェクトへコピーしたTopcoat UIコンポーネントを使用する。
- Topcoat UIコンポーネントは必要なものだけを取り込み、コピー後のソースをこのリポジトリで編集・保守する。
- スタイリングにはTopcoat組み込みのTailwind連携を使用し、本番環境にNode.jsランタイムを必要としない。
- Topcoat UIの標準デザインを基調とし、投票アプリに必要な余白、配色、および状態表示を調整する。
- 独自デザインシステムの構築はMVPの対象外とする。
- MVPは単一のアプリケーションインスタンスとして動作させる。
- Linux上で動作するOCI互換コンテナイメージを作成する。
- デプロイ先のプロバイダーは固定せず、SQLite用の永続ボリュームとSSE接続を保持できる実行環境を必要とする。
- MVPでは複数インスタンスへの水平分割を行わない。
- TopcoatとSQLxの依存更新は自動追従させず、変更履歴と互換性を確認して明示的に行う。

## リアルタイム更新

- 投票、投票先変更、締切は通常のHTTPリクエストとして処理する。
- サーバーから参加者への更新通知にはServer-Sent Events（SSE）を使用する。
- ブラウザでは外部SSEライブラリを使用せず、標準の`EventSource` APIを使用する。
- SSEでは表示データそのものではなく、投票部屋が更新されたことを通知する。
- 通知を受信したブラウザは、Topcoatの部分更新を利用して最新の表示を取得する。
- Topcoat 0.4系はSSEを直接サポートしないため、SSEエンドポイントとブラウザ側の接続処理をアプリケーションで補う。
- SSEの通知受信時、接続確立時、再接続時、およびブラウザタブが再表示された時に、結果表示部分の最新HTMLだけを取得する。ページ全体は再読み込みしない。
- Topcoat 0.4.0にshard更新を外部から起動する公開APIがある場合は、そのAPIを使用する。
- 適切な公開APIがない場合は、結果表示用のHTML断片エンドポイントと、標準`fetch` APIで取得した断片を結果領域へ反映する最小限のJavaScriptを実装する。
- SSEサーバーは15秒ごとにコメント形式のheartbeatを送信する。
- 切断中の通知は保存・個別再送せず、再接続時の結果表示再取得によって同期する。
- 画面上にSSEの接続中または再接続中の状態を表示する。
- リバースプロキシや実行環境はSSEレスポンスをバッファリングせず、長時間接続に十分なアイドルタイムアウトを設定できるものとする。

## データ保存

- 投票部屋、選択肢、参加者、および投票はSQLiteへ永続化する。
- DBアクセスにはSQLx 0.9.0のSQLite driverを使用し、依存バージョンを完全固定する。
- SQLxはdefault featuresを無効にし、Tokio runtime、bundled SQLite、migration、deriveに必要なfeaturesだけを有効にする。
- スキーマ変更はsqlx-cli 0.9.0でSQL migrationとして作成し、アプリケーションのデプロイ前に適用する。
- migrationの適用履歴はSQLx標準の`_sqlx_migrations`テーブルで管理し、独自の履歴管理は実装しない。
- アプリケーションはmigrationをバイナリへ埋め込み、起動時に適用済みmigrationのversionとchecksumが埋め込まれたmigration一式と一致することを確認する。起動時のmigration自動適用は行わない。
- RustのDB row/domain型と実行時検査の`query`/`query_as` APIを使用する。Issue #5ではcompile-time query checkingとoffline metadata管理を採用しない。
- 投票、投票先変更、締切など複数の読み書きを伴う処理はトランザクション内で実行する。
- SQLiteは単一ファイルDBと1接続に固定したpoolを使用する。
- `SqliteConnectOptions`で全接続に`foreign_keys(true)`、`journal_mode(SqliteJournalMode::Wal)`、busy timeoutを設定する。busy timeoutの既定値は5秒とし、DBファイルパスとともに環境変数で変更可能にする。
- 締切と投票が競合した場合は、先にコミットした操作を有効にする。締切が先なら投票を拒否し、投票が先ならその票を結果へ含める。
- 参加者と投票部屋の組み合わせに一意制約を設け、一人の参加者に複数の投票レコードを作成しない。投票先の変更は既存レコードの更新として扱う。
- アプリケーションの再起動後も、発行済みの参加用URLと投票結果を利用可能にする。
- SQLiteデータベースを保持する永続ボリュームを必要とする。
- MVPでは投票部屋と関連データを自動削除せず、締切後も参加用URLから結果を確認できるようにする。
- 表示名の入力画面では、表示名が締切後の結果にも残ることを案内する。
- 通常のアプリケーション再起動と再デプロイではデータを保持するが、永続ボリュームの故障や削除からの復旧は保証しない。
- 自動バックアップ、復元、およびアプリケーション内のデータエクスポートはMVPの対象外とする。

## ブラウザの識別と作成者権限

- 参加用URLには128bit以上の暗号学的に安全な乱数から生成した識別子を使用する。
- 参加用URLは閲覧と投票のために共有できる識別子とし、作成者トークンをURLへ含めない。
- 投票部屋の作成時に、推測困難な作成者トークンを発行する。
- 作成者トークンは`HttpOnly`、`Secure`、`SameSite=Lax`属性を持つCookieへ保存する。
- サーバーは作成者トークンのハッシュだけをSQLiteへ保存する。
- 選択肢の編集と締切では、作成者トークンを照合して権限を確認する。
- Cookieの削除や別ブラウザへの移動によって失われた作成者権限は復旧しない。
- 投票部屋ごとに推測困難な参加者トークンを発行し、同じ属性のCookieへ保存する。
- サーバーは参加者トークンのハッシュだけをSQLiteへ保存し、表示名を参加者の識別子として使用しない。
- 匿名の投票部屋でも参加者トークンを使用し、既存票の投票先変更か新規投票かを判定する。
- 公開される表示名は同じ投票部屋内で重複してよい。
- 作成者も通常の参加者として投票できる。作成者トークンと参加者トークンは分離し、作成者権限を一票の識別に使用しない。
- 投票者名を公開する部屋では、作成者も初回投票前に表示名を入力する。

## セキュリティ範囲

- 本番環境ではHTTPSを必須とする。
- Cookie、作成者権限、および投票可能な状態を、更新処理ごとにサーバー側で検証する。
- 状態を更新するHTTPリクエストでは`Origin`ヘッダーを検証する。
- 利用者入力はTopcoatの通常のエスケープを通して描画し、生HTMLとして扱わない。
- レート制限、CAPTCHA、荒らし対策、および厳密な多重投票防止はMVPの対象外とする。
- URLを共有された身内グループによる小規模利用を脅威モデルとし、一般公開サービスとしての濫用耐性は保証しない。

## 投票部屋の編集

- 作成者は、最初の投票が記録されるまで質問と選択肢を編集できる。
- 最初の投票が記録された後は、質問と選択肢を変更できない。
- 編集可否は画面表示だけに依存せず、サーバー側で検証する。

## 締切

- 作成者は総投票数が0でも投票部屋を締め切ることができる。
- 締切は不可逆とし、投票部屋を再開する機能を設けない。
- 同じ投票部屋への締切操作が複数回送信された場合は、締切済みの同じ結果を返す。
- 締切後の投票、投票先変更、質問編集、および選択肢編集をサーバー側で拒否する。
- 投票部屋を削除する機能はMVPの対象外とする。

## 入力検証

- 質問は1〜200文字、各選択肢は1〜100文字、表示名は1〜30文字とする。
- 文字数はUnicode書記素クラスタ単位で数える。
- 入力値の前後の空白を除去し、空文字と制御文字を拒否する。
- Unicode文字と絵文字を許可する。
- 一つの投票部屋内で、前後の空白を除去した後に完全一致する選択肢を拒否する。
- 選択肢の重複判定では、大文字と小文字の差やUnicode正規化による同一性までは判定しない。
- 入力検証はブラウザとサーバーの両方で行い、サーバー側の検証を正とする。
- 複数の入力に問題がある場合は、各入力欄へ対応付けられる検証エラーを一度に返す。

## 結果計算

- 各選択肢の割合は、その選択肢の票数を総投票数で割って算出する。
- 割合はサーバー側で計算し、小数第1位へ独立して四捨五入する。表示割合の合計が厳密に100%にならない場合を許容する。
- 総投票数が0の場合は、すべての選択肢を`0.0%`と表示する。
- 締切後は最多票の選択肢をすべて強調し、同率最多を表現する。
- 総投票数が0のまま締め切られた場合は、勝者なしとしてどの選択肢も強調しない。

## テスト

- Rust単体テストで入力検証、得票割合、および同率最多の判定を検証する。
- 一時SQLiteデータベースとアプリケーションと同じSQLx pool/queryを使用する統合テストで、投票、投票先変更、一意制約、締切との競合、および作成者権限を検証する。
- PlaywrightによるE2Eテストで、投票者名を公開する部屋と匿名の部屋の主要フローを検証する。
- SSEのE2Eテストでは独立した二つのブラウザコンテキストを使用し、一方の投票がもう一方へページ全体の再読み込みなしで反映されることを検証する。
- SSEの切断と再接続後に、結果表示が最新状態へ同期することをE2Eテストで検証する。
- PlaywrightとNode.jsはテスト専用とし、アプリケーションの実行時依存やクライアントビルドには使用しない。
- テスト、静的解析、およびコンテナビルドはローカルで実行可能にする。
- GitHub Actionsでは、Pull Requestと`main`へのpushを対象に、`cargo fmt --check`、警告をエラー扱いする`cargo clippy`、Rust単体テスト、およびSQLite統合テストを単一ジョブで実行する。
- GitHub ActionsではPlaywright E2Eとコンテナビルドを実行せず、ローカル確認とする。
- 同じブランチで新しい変更がpushされた場合は、実行中の古いワークフローをキャンセルする。
- ドキュメントだけの変更ではGitHub Actionsを起動しない。
- CIではテスト成果物を保存しない。

## 対応ブラウザ

- 最新のChrome、Firefox、Safari、iOS Safari、およびAndroid Chromeを対象とする。
- スマートフォンとデスクトップの画面幅に対応する。
- SlackとDiscordの内蔵ブラウザはベストエフォートで対応する。
- Internet Explorerおよび古いブラウザは対象外とする。
- 通常のE2E確認にはChromiumを使用し、節目でFirefoxとWebKitをローカル確認する。

## アクセシビリティ

- マウスを使用せずに、投票部屋の作成、入室、投票、投票先変更、および締切を操作できるようにする。
- 選択肢は意味的に適切なラジオボタンとして実装する。
- フォームのラベルとエラー説明を対応する入力要素へ関連付ける。
- キーボードフォーカスを視覚的に表示する。
- 締切状態、選択中の項目、および最多票の結果を色だけで表現しない。
- 結果表示の部分更新をスクリーンリーダーへ通知する。
- 文字と主要UI要素に基本的な色コントラストを確保する。
- Topcoat UIコンポーネントを編集した後の実装が、これらの受け入れ条件を満たすことを確認する。

## ログとヘルスチェック

- Rustの`tracing`を使用し、HTTPリクエスト、エラー、投票部屋作成、投票、および締切を記録する。
- 作成者・参加者トークン、Cookie、表示名、および投票先をログへ記録しない。
- 本番環境ではJSON形式、ローカル開発では人が読みやすいテキスト形式で標準出力へログを出力する。
- `/healthz`でプロセスがHTTPリクエストへ応答できることを確認できるようにする。
- `/readyz`でSQLiteへの接続と必要なマイグレーションの適用を確認できるようにする。
- 外部監視、メトリクス収集、およびエラー通知サービスはMVPの対象外とする。

## 性能目標

- 1投票部屋あたり30人程度の同時参加を設計目標とする。
- アプリケーション全体で100本程度の同時SSE接続を設計目標とする。
- 通常時は、投票の受付後1秒以内に他の参加者の結果表示へ反映することを目標とする。
- これらはアプリケーションが参加や接続を拒否するハードリミットではない。
- 専用の大規模負荷試験はMVPの対象外とし、ローカルでの簡易確認に留める。
